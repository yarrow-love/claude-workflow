# Work Order

The canonical, type-polymorphic workflow for advancing one work order (`type: feature | bug | refactor | chore`) to completion. Invoked as `/execute <work-order>`; the autonomous variant applies the [work-order-automatically](execute-work-order-automatically.md) overrides. Roles and policies (consultation, model tiers, delegation): [manager/CLAUDE.md](../CLAUDE.md). Filing conventions and per-type document structures: `work/todos/README.md`.

## Entry state

**The work order is the state machine — advance it from wherever it stands:**

- **No plan section** → run the full sequence from step 1.
- **Approved plan present** (a completed plan section, typically via `/plan`; status `planned` or `in-progress`) → verify the `## Blessing` section exists: a blessed order sets status `in-progress` and enters at step 9; an approved-but-unblessed plan runs step 7 (blessing) first. Do not re-investigate or re-plan; the plan was approved when it was written. Post-review consultation still applies (step 11), but there is no step-8 pause to re-run.
- **`## Progress` ledger present** (a prior automatic-mode run ended mid-flight) → resume at the last logged transition; honor any recorded verdict residuals.

## The sequence

1. **Read the referenced work order.** *bug*: read the report(s) and synthesize duplicate/related reports into one.
2. **Investigate** (type-specific, read-only):
   - *feature / refactor*: dispatch researcher to explore the codebase and relevant architecture.
   - *bug*: dispatch investigator to trace root causes.
   - *chore*: skip unless the filing leaves genuine unknowns.
3. **Format the document** — revise the filing section; add the findings section (section names per type: `work/todos/README.md`). Rename/move the file to the dated convention if the filing predates it.
4. **Interview the user** — raise clarifying questions as needed; await confirmation.
5. **Dispatch the planner** to develop the plan from the findings — model per the work order's frontmatter `difficulty` (the manager model-tier policy).
6. **Write the plan section** to the work order.
7. **Submit for blessing** — the mandatory Architect gate (policy: the manager's Architect Blessing section). Present the prepared work order whole to the Architect for **blessing or critique**: consult-fork the standing handle when the `sessions:` frontmatter carries one (the last `architect@…` entry, machine-local — the spec's author judges whether the order serves its intent); otherwise dispatch a fresh architect subagent. Always flagship (`fable`, falling back to `opus` if unavailable), regardless of `difficulty`. Verdict: `BLESSED`, or numbered critique directives. On critique: dispatch a **fresh planner** briefed with the numbered critique directives and pointed at the prior plan in the work order (restored by reading), collect its revision in-turn — revise the plan section, resubmit — bounded at **two rounds**; unresolved after the bound → carry both positions to the sign-off (step 8). Append the stamped `## Blessing` section recording the verdict and any directives with their resolutions.
8. **Present the blessed order** — the plan brief, the planner's itemized **Decision points** block (one line per decision: choice, rejected alternative, consequence — recommendation marked), and the Blessing verdict (including any unresolved critique); await sign-off on the order **as documented**. **This is the workflow's one mandatory checkpoint.**
9. **Dispatch implementer subagents** per plan phases — dependent phases sequentially in dependency order; independent phases in parallel (one message, multiple agents). Every ledger line recording a dispatch carries the child's `agentId` (`work/todos/README.md` § Document structure — the dispatch record).
10. **Dispatch the reviewer** over all code changes.
11. **Act on review findings** — resolve mechanical findings directly and record them in the Code Review brief; pause to consult the user only when a finding reopens a design decision (architecture, data model, security trade-off, scope). **Before pausing**, if the work doc's `sessions:` frontmatter carries a consultable planning handle (the last `architect@…` entry, machine-local), run the architect consult per the manager's Planner Callback policy — a *technical* question the operator isn't equipped to answer often is an interpretation question the plan's author can settle; if it resolves as interpretation, proceed without pausing; if it's genuinely a new decision, pause **with the consult's analysis attached**.
12. **Run the project quality gate** (`work/PROJECT.md`); if it fails, split by judgment: an *obvious* failure (syntax error, missing import, path typo) → dispatch a **fresh implementer** briefed with the gate output and the phase's diff — no investigator; a *non-obvious* failure → dispatch a **fresh investigator** for diagnosis (failure diagnosis must not inherit the builder's assumptions), then a **fresh implementer** executes the fix, briefed with the report alongside the gate output and the phase's diff.
13. **Verify activation** — trace the change from the user's entry point (CLI command, route, UI interaction) to confirm it is on the active code path. If any env var toggle, conditional branch, or commented-out block gates the new code, remove the gate and the old path.
14. **Inspect** — if frontmatter `scope` includes `interface` (or implementation touched the project's front-end surface): dispatch the inspector to verify UI outcomes. Target per type: *feature/chore* — acceptance criteria; *bug* — the fix visually functions (the reproduction no longer reproduces); *refactor* — no visual regressions against existing behavior. On FAIL/PARTIAL: dispatch investigator + implementer to resolve, then re-inspect. **The taste gate**: when the order references a design brief (`work/design/sessions/…/BRIEF.md`), inspector PASS verifies *conformance* but never closes the *design* question — stage the operator's design acceptance as an **operator-gated** item (surface the inspector's screenshots; in automatic mode, list it under the Acceptance Verdict rather than blocking).
15. **Write the Summary** (include the Front-end Inspection section if the inspector was dispatched).
16. **Documentation wrap-up — deputize, don't re-derive.** Dispatch a **fresh implementer in a documenter hat**, briefed with the diff of the phase that touched the affected behavior plus the work order — the intent behind the change is legible there, so the brief deputizes rather than reopens it: revise the docs affected by *that* change, bound by the documenter's conventions (`documenter.md`: accuracy over completeness, current-state prose, the supplement's never-touch list). Stamp the section `documenter@<machine>/<session>` — the role names the act. When the change spans many phases, widen the brief from one phase's diff to the work order's Summary + commit list. Either way the brief stays order-shaped — this is the wrap-up, scoped to what this order changed, not the whole-surface sweep a `/document` standing audit runs; rationale: the Dispatch classification table in [manager/CLAUDE.md](../CLAUDE.md).
17. **Reconcile milestone + footgun ledgers** — if the work completes a milestone phase: update the corresponding `work/milestones/` entry and reconcile the footgun ledger (`work/footguns/` + the CLAUDE.md index — add new, trim resolved) in the same `Document:` commit. *bug*: if the resolved bug closes a footgun entry, delete it or demote it to a runbook/script comment in the same commit.
18. **File the completed order** to `work/todos/_done/`, preserving the filename. *bug*: first add a descriptive `resolution:` line to the frontmatter and a `## Resolution (<date>)` section to the body.
19. **Triage bugs filed mid-flow** — list each `work/todos/bugs/<today>.bug.*.md` filed during this workflow with brief notice (severity, scope-of-fix estimate, recommendation). Resolve trivially-resolvable items while context is fresh, riding the adjacent implementer's context when one exists (documented `resolution:` + Resolution section, filed to `_done/`); offer investigation of the rest as an optional follow-up — the user opts in per bug; never investigate automatically. Only bugs genuinely requiring their own `/execute` session remain in `work/todos/bugs/` at session end.
20. **Hygiene checklist (advisory).** Wear the [janitor](../../janitor.md)'s hat for a light pass over what this order touched: is the tree still consistent with the parts of the structure declaration (`work/PROJECT.md` § Structure) the order reached? Route findings by `janitor.md` § The remedy ladder — mechanical fixes ride the commit below, everything else is noted or filed. **Advisory: it never blocks this close** — whole-repo drift is invisible at order scale (policy and rationale: [manager/CLAUDE.md](../CLAUDE.md) § Closing Out); the blocking pass belongs to the milestone close ([execute-milestone](../../executor/workflows/execute-milestone.md)).
21. **Commit** changes as related groups (one commit per phase or logical unit) — the close-out fires on completion, before any reply prose (`work/README.md` § The follow-through rule). Standing approval — no confirmation required. Imperative `Add:` / `Fix:` / `Update:` / `Organize:` prefixes, Co-Authored-By footer; never `git add -A` or `git add .` (always enumerate paths). The child-collection rule binds this turn-end as it binds every other ([manager/CLAUDE.md](../CLAUDE.md) § Turn discipline).

## Format

Document naming, frontmatter vocabulary, and the per-type `<h2>` section structures live in `work/todos/README.md` — follow them exactly. Revise for brevity and consistent voice (the manager authors every section; subagent output is distilled, never pasted); sections separated by `---`; each appended section prefaced by your callback stamp per `work/README.md` § The callback grammar.
