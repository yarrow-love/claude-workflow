# Repo hygiene — the Janitor competency, the `/clean` verb, and the declared-structure floor

> Proposal, 26-07-25, from an operator dialog. Seeding evidence: a formal request from the Orchestra dogfooding project (`~/dev/orchestra/work/notes/26-07-25.repo-hygiene.md`, addressed to this session's handle), carrying the record of an operator-directed `src/` reorganization (`orchestra work/todos/_done/26-07-25.src-reorg.refactor.md`) and the repo's first `/triage`. The workflow is now dogfooded in at least two consuming projects (`~/dev/lasers`, `~/dev/orchestra`); both exhibit the same drift. Operator determinations already made in-dialog: mission tier on branch `26-07-25` (mission `v2.repo-hygiene`); the milestone-boundary gate is **blocking**; the verb is **`/clean`**.

## The problem (as evidenced, not hypothesized)

Consuming projects drift toward disorder even when the work is good — and the drift is structural, not negligent. The template *states* hygiene as a value in prose but assigns it to **no role and no gate**; a policy with no owner is aspirational. The Orchestra note names four mechanisms, all confirmed by the evidence:

1. **Objective focus** — acceptance criteria measure capability, never structure; hygiene is orthogonal to every acceptance test.
2. **Bounded vision** — each specialist sees one scoped slice; structural drift is a whole-repo emergent property no bounded task can see.
3. **Gate coverage** — the quality gate checks functional correctness; nothing checks organizational structure.
4. **Prose without an owner** — README conventions hold only while every author happens to remember them; under objective pressure, they don't.

The evidence classes (abstracted from Orchestra): tooling colonizing the organizational root; product and non-product code as flat peers; the work inbox accreting closed orders with stale status. All three are one meta-pattern: **actual state drifts from declared convention because no role reconciles them, and the drift is invisible to objective-focused work.**

## The invariant floor — declaredness + reconciliation

The Orchestra note's Proposal A offered five candidate invariants (root discipline, product/non-product separation, tracked-tree cleanliness, whole-canon reference integrity, work-tracking fidelity). Four of the five are not universally *specifiable* — some ecosystems force root files (`.github/`, toolchain configs, CI manifests), so any fixed allowlist the template ships is wrong somewhere. The true **maximal-minimum universal** is the meta-pattern itself, inverted:

> **Every consuming project declares its structure; the system owns reconciling actual against declared.**

- **Declarations** live at the existing project-specifics seam — `work/PROJECT.md` gains a **§ Structure** section (root-file allowlist, product/non-product boundary, package-root placement, archive convention), authored at bootstrap with **template defaults** the project amends rather than invents. `.claude/` stays perfectly project-generic: it ships the *axes and the mechanism*, never the project's facts.
- The five Proposal-A items survive as the **audit axes** of reconciliation — the questions every `/clean` pass asks — with their project-specific content read from the declaration.

## The Janitor — a staff competency worn at boundaries

**Ladder position: staff authority, not executive.** The Janitor audits, routes, and gates; it holds no campaign context and never performs structural surgery inline. Its nearest kin is the Architect (advises and directs, never dispatches builds) — an inspector-general. The reviewer is to code-correctness what the Janitor is to repo-structure.

**The hat pattern (precedent: Planner/Architect are "the same competency at different tiers").** The competency is defined once — `.claude/agents/janitor.md`: the audit axes, the declaration-reading protocol, and the three-rung remedy ladder — and is **assumed by whichever session presides at a boundary** rather than freshly dispatched:

| Boundary | Who wears the hat | Depth |
| --- | --- | --- |
| Work-order blessing (plan time) | Architect | Hygiene lens on the blessing checklist: does the plan state where artifacts land, consistent with the declaration? |
| Work-order close | Manager | Light checklist: did this order leave the tree consistent with the declaration it touched? |
| Milestone close | Executor | **Full pass, blocking** — the milestone cannot close until the pass runs clean or its contestable findings are explicitly escalated |
| On demand | `/clean` (operator-run) | Full pass in authority mode, judgment-closed, like `/design` |

**The three-rung remedy ladder** (proven by the Orchestra evidence — stale frontmatter and path fix-ups were safely mechanical; naming `src/_/` and relocating the package root were operator calls):

1. **Auto-fix the unambiguous** — mechanical reconciliations (archiving closed orders, status frontmatter, dangling references, ignore-file entries) applied inline, committed with enumerated paths.
2. **File the structural** — findings above the mechanical threshold become **typed remedy work orders** (the Orchestra `src/` reorg is the exemplar) that flow through normal blessing and execution with a plan and verification. The Janitor directs; it does not operate.
3. **Escalate the contestable** — genuine structural forks (naming, boundary placement, relocation) go to the operator. In automatic mode, an unresolved fork is an **ESCALATE halt**, mirroring the Blessing gate's semantics.

**Prevention needs no new machinery.** The Blessing gate is already the plan-time chokepoint every work order passes; it acquires the hygiene lens. Planning artifacts (milestone phase docs, work-order plans) gain a required *where-artifacts-land* statement for the lens to verify. New code cannot land in the wrong place without the plan having misstated it to the Architect first.

**Composition, not duplication.** `/clean` orchestrates the existing slice-audits — `/triage` (inbox fidelity), the reference-resolution gate (whole-canon, generalized from its `.claude/`-scope), doc-drift detection — and adds the one missing axis: source-tree structure vs declaration. One boundary pass that leaves the repo clean, not a fourth overlapping tool.

## Open forks — the alignment agenda before chartering

1. **Declaration home**: `work/PROJECT.md § Structure` (recommended — one seam, already read by every role) vs a dedicated `work/STRUCTURE.md`.
2. **Auto-fix threshold**: the precise line between rung 1 and rung 2 — propose: *anything expressible as a move/rename/status-edit with zero judgment calls and a passing reference-gate afterward* is rung 1; everything else files.
3. **`/triage` relationship**: `/clean` *invokes* triage as one axis (recommended) vs subsumes it vs leaves it fully independent.
4. **Work-order-close checklist strength**: advisory (recommended — the blocking gate lives at milestone scale; order-scale blocking would tax every order for whole-repo drift it can't see) vs blocking.
5. **Reference-integrity generalization**: extend the existing `.claude/`-scoped reference gate to the whole canon (recommended) — confirm the cost is acceptable at `/clean`-time only, not per-commit.
6. **Mission shape**: M1 settle the floor into canon (this proposal → doctrine) · M2 build janitor.md + `/clean` + gate wiring + prevention statements · M3 dogfood-validate on the mission's own tree, fold to main, purify. Confirm or amend.
