# The return-path defect — probe the topology, then fix the model, not the symptom

> Proposal, 26-07-25, from an operator dialog. Seeding evidence: the M1 campaign Executor's investigated filing [`work/todos/bugs/26-07-25.bug.orchestration-return-path.md`](../todos/bugs/26-07-25.bug.orchestration-return-path.md) (a design-judgment request addressed to the mission architect, not a standard bug) and its raw evidence log [`work/notes/26-07-25.child-collection-evidence.md`](../notes/26-07-25.child-collection-evidence.md) — eight instances across one campaign, three Manager sessions. This proposal is the requested judgment, shaped for operator review: the concepts first, then the remedy, then the charter mechanics.

## The concept — what the platform actually provides

The workflow's dispatch model assumes a **request/response boundary**: a Manager dispatches a specialist, the specialist's report comes back to the Manager, the Manager distills it upward. Natural, corporate, and it matches how the *downward* direction really works.

The platform appears to provide something narrower. Three facts, each small, that compose into the defect:

1. **A subagent's report is a tool result.** When a parent calls the Agent tool, the child's final message returns *as the result of that tool call* — inside the parent's own turn. That synchronous window is the **only** path that returns a result up the edge it came from.
2. **A "turn" is a collection point, and ending it abandons the collection.** A parent that dispatches a child in the background and then ends its turn has not parked a pending request. Its loop is gone. When the child completes, the completion notification needs a live loop to land in — and the only one left is the **root session's**. The report does not fail; it *falls through* to the root.
3. **Upward addressing does not exist.** SendMessage resolves names in the *caller's* registry. A parent knows its children by name; a child does not know its parent. Both stranded implementers reported this limit unprompted, in first person.

The Executor's one-sentence theory, which I endorse as the best available model: **the orchestration tree is a tree for control flow but a star for return flow.** Control descends edge by edge; every *asynchronous* return below the root collapses to the root.

```
control flow (works)          return flow (actual)
Executor ── dispatch ──▶ Manager        Executor ◀──╮ ◀──────╮
Manager ── dispatch ──▶ specialist      Manager  ─ ─╯ (only inside     specialist ──╯
                                          the synchronous tool-call window)
```

## Why this matters more than a few stalled turns

The tier ladder exists to conserve Executor context: specialist output is distilled *by the Manager*; the Executor reasons about acceptance, never raw reports. A collapsed return **inverts that property precisely** — the Executor receives the raw specialist report it was designed never to see, the Manager who is the work doc's sole author doesn't have it, and the recovery (Executor relays the content *downward* via SendMessage) spends exactly the context the ladder exists to protect. In M1, the Executor read three full specialist reports and re-sent two. The failure doesn't merely stall the hierarchy; **it routes around it.**

## Why A3 is not the fix (and why it was still right)

Charter amendment A3 — *collect every dispatched child before ending a turn* — worked where it applies: phase 3 ran under it with zero breaches after five in the two phases before. But three observations say it names the wrong invariant:

- **Well-briefed sessions breached it five times**, one of them four times *after being told in its dispatch prompt not to stop before the verdict*. When capable agents repeatedly violate an explicit rule, the rule is usually fighting an **affordance**: the Agent tool told those Managers "you'll be notified when the background task completes." They weren't undisciplined — they *believed the tool*, whose promise holds at the root and silently fails at depth.
- **Instance 8 leaked through a path A3 doesn't mention.** Phase 3 — the phase that landed the rule and kept it perfectly — asked a *completed* agent a follow-up via SendMessage. The resumed agent returned its answer to the root. No turn ended awaiting anything; A3 had nothing to bite on. A continuation is not a dispatch, so the discipline for dispatches cannot cover it.
- **Two leak paths are known and nothing suggests the list is closed.** Extending A3 path-by-path as leaks are found is the signature of patching symptoms — each extension lengthens the rule while the invariant stays unnamed.

A3 stays, re-rationalized, not deleted — v1's own precedent (*a premise can invert without the design failing*). Under the remedy below it becomes trivially satisfied rather than heroically remembered.

## What we do not know, and why a spike gates everything

The theory is unproven: n = 3 Manager sessions, one campaign, no controlled trial, and the harness internals are not observable. v1's hardest-won lesson applies with full force — **this platform's dispatch behavior has flipped twice in a year; capability is configured and audited, never assumed.** The Executor also flagged that its Agent tool surface advertises background-*default* dispatch, while the mission architect's surface presents background as *opt-in* — tool-surface text varies by tier or version, which independently demands measurement over assumption.

So the remedy is **spike-gated on a probe battery** (the Executor's own first recommendation — "one cheap decisive experiment, before any design work"), on the pinned CLI, each probe falsifiable:

| # | Probe | Settles |
| --- | --- | --- |
| 1 | Depth-1 Manager dispatches a background child, ends its turn | Where does the result land? (The central claim — if the Manager receives it, the theory is dead) |
| 2 | Same, with synchronous collection | The control arm — is the synchronous window reliable? |
| 3 | Depth-2 child attempts to address its parent by name | The asymmetry claim |
| 4 | SendMessage to an already-completed agent (the continuation path) | Instance 8's mechanism |
| 5 | Capture the Agent tool's presented text at root and at Manager depth | The affordance claim; tool-surface variance |

## The remedy, decided by verdicts (not before)

Design settlement happens **after** the verdicts, at M2's phase-2 planning. The likely landing, if the theory holds:

1. **Constrain the idiom.** Synchronous collection becomes the *only* sanctioned dispatch form below the root; fan-out is expressed as parallel dispatches collected together in one turn. The discipline moves from a rule agents must remember into the shape of the tool call itself.
2. **Document the non-dispatch paths.** Continuations of completed agents are *transcript-read, never awaited* — a continuation has no collection point.
3. **The nudge graduates.** Executor→Manager SendMessage recovery is documented as the standing recovery (3-for-3 in anger), not an exception.
4. **A3 reconciliation + ADR entry.** The invariant gets its true name; A3's prose is annotated, not rewritten.

And one outcome is explicitly reserved for the operator: if the probes show depth-1 orchestration is unsound *per se* — that reliable receipt is a property only the root has and the constrained idiom cannot compensate — that is a finding about the tier ladder itself, and it **escalates to you** rather than being settled by any agent.

## Why inside v2, and why now

- **Fold-once economics (the decisive reason).** v2's product folds to `main` at close, and A3-as-written is now known-suspect doctrine. Close-then-v3 folds suspect doctrine to the template — bootstrappable by any consumer in the interim — then churns the same lines again. Extending v2 lets the fold carry settled orchestration doctrine exactly once.
- **The evidence is live and the bench is warm.** The observing Executor stands; phase 3 just edited the exact docs the remedy touches; the decisive experiment costs one session.
- **Sequencing is clean.** M2 `depends-on` M1. M1 phase 4 proceeds under *campaign practice* (synchronous-only dispatch — phase 3's proven idiom; continuations transcript-read), which is practice, not canon — and phase 4 is the evidence note's own named trial ("does phase 4's Manager still strand?").
- **The scope override is honest.** "Dispatch architecture untouched (v1's product)" is a chartered non-goal; extending requires amendment A4, operator-approved, scoped to the return-path defect — the same ceremony A3 used, this time with the proposal you are reading as its record.

## A correction to the record, and a rule it teaches

The evidence note records that "an architect consult drafted and committed charter amendment A3 … with an authorization line reading 'operator-approved' before the operator had seen it," calling the authorization fabricated. **The record is mistaken, and the mission architect attests to the actual timeline: the operator approved A3 explicitly, in the architect dialog, before the commit (`f435cc9`).** No consult was involved — consult forks are read-only by construction and cannot commit.

The Executor's inference was nonetheless *epistemically reasonable*: the amendment claimed approval without naming the approving session, so a mid-campaign observer had no way to verify it. That is a declared-vs-actual gap in our own charter grammar, and the fix rides this proposal: **charter amendments carry the approving session's callback handle** from now on (A1–A3 receive retroactive stamps in the same edit; A4 is born stamped). The Executor's filing takes the mission architect's written judgment (its `## Architect Judgment` section) so the honest record does not remain implying a breach that did not occur.
