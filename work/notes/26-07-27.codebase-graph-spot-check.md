## The process-count false green

The process-check is the highest-stakes seam value, and the form an agent reaches for by instinct is **wrong on this OS**. Four measurements, 26-07-27, verbatim — stdout, stderr and exit code separated, because the separation is the finding:

```
$ ps -C codebase-memory-m --no-headers | wc -l
6

$ pgrep -x codebase-memory-mcp; echo "exit=$?"
                                                          # stdout: empty
pgrep: pattern that searches for process name longer than 15 characters will result in zero matches
Try `pgrep -f' option to match against the complete command line.
                                                          # ^ both lines are stderr
exit=1

$ pgrep -c -f codebase-memory-mcp
7                                                         # exit=0

$ pgrep -c -x -f /home/yarrow/.local/bin/codebase-memory-mcp
6                                                         # exit=0
```

Ground truth is **6**. `pgrep -x` reads **0** — the shape of a satisfied precondition.

**The mechanism.** Linux truncates `/proc/<pid>/comm` to 15 characters. Read directly: `cat /proc/595420/comm` → `codebase-memory`, length **15**. The binary basename is `codebase-memory-mcp`, length **19** — *the work order's prose says 20; the count is 19, and the correction is recorded here rather than propagated*. `pgrep -x` matches its pattern against the **whole** `comm` string, so a 19-character pattern can never equal a 15-character string, for any number of running processes. `ps -C` truncates the *pattern* to 15 before comparing, which is why all three of `ps -C codebase-memory-mcp`, `ps -C codebase-memory-m` and `ps -C codebase-memory` return **6**. Measured on `procps-ng 4.0.6-dirty`.

The seventh match under `pgrep -c -f` is the invoking shell — PID 1475754, `/usr/bin/zsh -c source …`, whose own command line contains the pattern. That is why the unanchored `-f` form over-counts by exactly one and the absolute-path `-x -f` form does not.

**Why it matters, and it is not trivia.** A zero from a wrong command is indistinguishable from a satisfied precondition. A run that accepts it proceeds against a **wedged** store — six holders blocking WAL checkpointing — and then reads the contention artifacts (a silently no-op'd re-index, a stale flip result, an `expected_*`/`actual_*` mismatch) as **falsified discriminants**, manufacturing a spurious `ESCALATE` against a protocol that is in fact correct. This is the same false-pass shape the protocol already names for `path` versus `file_path`: "zero rows is exactly what a clean result looks like."

**The sharpening, checked rather than assumed: this procps *does* emit a stderr diagnostic** — the two-line warning above, plus exit code **1**. So the false green is not silent at the terminal. It is silent under every idiom an agent actually writes:

```
$ pgrep -x codebase-memory-mcp 2>/dev/null | wc -l
0
$ pgrep -c -x codebase-memory-mcp 2>/dev/null
0                                                         # exit=1
```

`2>/dev/null` discards the warning outright. `| wc -l` and `-c` keep the warning on stderr but convert an **empty stdout** into the printed digit `0` — and a printed `0` is what gets compared against the precondition. A `$(…)` capture or a `|| true` swallows the non-zero exit that was the other signal. In a harness that merges stdout and stderr into one blob, the warning survives but is one skimmable line above a number that reads as success. **The number is wrong in every form; only the diagnostic varies.** Hence the rule that belongs in canon (amendment B): validate the process-check command against a *known-nonzero* count before trusting it.
