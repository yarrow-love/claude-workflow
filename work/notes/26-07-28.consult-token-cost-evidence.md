# Empirical evidence: resume-fork consults pay the superior's full context on every call

> Filed 26-07-28 by `claude@antec/60e7afd1-7e91-46d1-aa17-f1f957a6ac9f` (operator dialog, in the `lasers` consuming repo) at operator direction. Pre-proposal: mechanism confirmed against `.claude/bin/consult` and measured against a live flagship transcript. The operator's report: since the callback intercom graduated from fresh headless `claude -p` dispatches to `--resume`-based callbacks, observability is a UX win but token consumption and wall-clock latency have regressed sharply. Graduates into `work/proposals/26-07-28.persistent-intercom-and-consult-economy.md`.

## The operator's theory, confirmed

The theory was: *when we resume a session, the full session context may be reloaded into a forked session.* This is exactly what happens, by construction, and there is no partial mode.

`.claude/bin/consult` builds `claude -p --resume <uuid> --fork-session …`. Resume rehydrates the recorded session's **entire live conversation state** into the fork before the consult question is read. The fork is a full copy of the superior's context; the question rides on top of it. Every consult therefore pays the whole superior-transcript prefix as input tokens — a cost proportional to the superior session's size, which grows monotonically over a mission's life.

The old pattern (fresh `claude -p` + documents) paid a per-call **flat** cost: system prompt, tool schemas, the question, whatever documents were attached. The graduation to resume traded that flat cost for the proportional one. The observability gain is real; this is its price mechanism.

## Measured, this machine (ANTEC), 26-07-28

**Transcript scale.** The flagship architect session `8c5a12c4-e2ce-4801-ab67-e4c097e1ca1a`:

| Where | Size |
| --- | --- |
| Durable archive (`work/sessions/ANTEC/…jsonl.gz`) | 37.4 MB compressed / 60.8 MB raw |
| Local cache (`~/.claude/projects/…/…jsonl`) | 59.4 MB |

The raw `.jsonl` overstates the live context (it carries event metadata and superseded pre-compaction turns), but the rehydrated context of a session at this scale is plausibly in the hundreds of thousands of tokens. The next four sessions in the local cache are 5.2, 4.8, 2.9, and 1.9 MB — an order of magnitude smaller, so the flagship-architect handle is precisely where consult traffic is heaviest **and** where each consult is most expensive.

**Floor cost.** A trivial fresh `claude -p "Reply with exactly: PING-OK"` (no resume, no documents) measured: 7,246 tokens cache-write + 24,269 cache-read + 7 output, $0.085, ~2.8 s wall. That is the baseline every dispatch pays regardless of pattern; the resume prefix stacks on top of it.

## Why it is slower *and* costlier: cache dynamics

The prefix cost is not constant — it depends on prompt-cache state at call time:

- **Consults clustered inside the cache TTL** hit the cached prefix: billed at ~0.1× input price, fast prefill. Tolerable.
- **Sporadic consults** — the typical intercom pattern, one question per phase boundary, spaced beyond the TTL — are worst-case: each is a full cache **write** of the entire prefix at 1.25–2× input price, plus prefill of the whole context before the first output token.

The prefill is the observed latency: the wait is not the answer being generated, it is the fork re-ingesting the superior's whole recorded life before reading the question. Both regressions the operator reported — tokens and speed — are the same mechanism seen from two sides.

**Fork-per-question multiplies it.** N questions asked as N consults cost N prefix loads. `--fork-session` keeps forks from polluting the superior's transcript (a property worth keeping in any successor), but it also means no consult ever amortizes the load for the next one except via the shared prompt cache — which sporadic spacing defeats.

## What an "open connection" would look like

The ideal the operator named — superior stays active while inferiors work, with a channel open, no full reload per exchange — exists in the CLI and is not `--resume`. Streaming input mode:

```
claude -p --input-format stream-json --output-format stream-json
```

holds the session as a **live process**: stdin stays open, successive user messages arrive as JSON events, each turn appends only the new exchange, and back-to-back turns on one conversation keep the prompt cache warm continuously. Observability is equal or better than resume-forks — stream-json emits every event (tool calls, token counts, subagent activity) as it happens; the Executor doc already reads these events for its `session_id`-at-launch and stall rules. The cost is lifecycle machinery: something must own the process (spawn, heartbeat, stall-kill, restart after reboot), which the current fork-per-question design gets for free by having no state between calls.

#### Four traps phase 2 must not fall into

The most valuable thing in this section. Each is a way to read the wire that produces a plausible, wrong number.

1. **`total_cost_usd` is CUMULATIVE per process, not per turn.** The five `result` events carry 0.217667 → 0.435894 → 0.654599 → 1.122662 → 1.593723. Per-turn cost is the **delta**, not the field. `usage` itself is *not* cumulative — it is per-user-turn, aggregated over that turn's internal model calls, which is why probe-1 shows a doubled `cache_read` alongside `num_turns: 2`.
2. **`system` / `init` re-fires once per turn (5×), not once per process.** All five carry the identical session id, tool registry, permission mode and model. A driver keying "a new session started" off `init` will mis-count sessions by a factor of the turn count.
3. **`assistant` events split one model call across content blocks — one event per block.** The 10 `assistant` events are only **7 distinct model calls**: three `message.id`s appear twice (`thinking` then `text`, or `thinking` then `tool_use`), each pair sharing one `request_id` and one identical `usage` object. **Summing `assistant.message.usage` naively double-counts.** De-duplicate by `message.id`, or simply use `result.usage`.
4. **`usage.iterations[]` is incomplete — it is not a per-call breakdown.** Probe-1's aggregate is `output_tokens: 562` while `iterations[]` holds a single entry with `output_tokens: 450` (the last model call only). Probe-2: aggregate 376, single iteration 136.

## Addendum — the reimplementation-grade record

> manager@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

### The stdin wire format

Newline-delimited JSON, one object per line. The accepted user-turn shape is the Agent SDK's `SDKUserMessage` lead, accepted on the **first** candidate tried — no fallback shape was needed:

```json
{"type":"user","message":{"role":"user","content":[{"type":"text","text":"…"}]}}
```

Four mechanics a reimplementation must carry, each of which fails silently if omitted:

- **The object must be newline-terminated.** The reader is line-oriented; an unterminated object is never dispatched.
- **Bun's `proc.stdin` is a `FileSink`, so `.write()` must be followed by `.flush()` on every turn.** Without the flush, turn 1 works and turn N+1 silently never arrives — it looks exactly like a model stall.
- **EOF comes from `proc.stdin.end()`, never `proc.kill()`.** The clean exit-code-0 evidence in criterion 6 exists only because EOF is the sole shutdown path; a kill destroys it.
- **stdout *and* stderr must be drained concurrently with the exit promise.** Both pumps start at spawn, structurally before any `await exited`. `--verbose` plus stderr warnings will otherwise fill an OS pipe buffer and deadlock the child, which presents as a slow model rather than as a hang.

Raw stdout bytes should be teed to the log *before* newline-splitting and `JSON.parse`; parse failures are logged and non-fatal, so one stray non-JSON line cannot destroy a run's evidence.

### The turn-completion signal

```json
{"type":"result","subtype":"success", …}
```

carrying `num_turns`, `duration_ms`, `stop_reason` (`"end_turn"`), `terminal_reason` (`"completed"`), `usage`, `total_cost_usd`, `permission_denials`. The working predicate is:

```js
ev => ev.type === "result"
```

**The process does not exit on `result`.** That is precisely what makes hold-open work: `result` closes a turn, EOF closes the process.

### Cost data — carried for phase 2

- **Phase C's full five-turn run: $1.593723 total.** Per-turn deltas: $0.2177 / $0.2182 / $0.2187 / $0.4681 / $0.4711.
- **That $1.59 is a *warm-channel* figure.** Turn 1 shows `cache_creation_input_tokens: 0` against `cache_read_input_tokens: 217,147` — the discovery run's 1h-ephemeral cache, written 12 minutes earlier, was still resident.
- **The cold fork figure is ~$4.262748**, with 212,899 tokens written to cache (`cache_read` only 4,248) — measured on the discovery run, which paid the full prefix write.
- **The post-mortem resume paid $0.233411** — `cache_read: 218,311` against `cache_creation: 174` and `input_tokens: 2`. That is a **~18× warm/cold ratio on the same prefix** ($4.262748 / $0.233411 = 18.26), obtained free as a by-product of criterion 6.

Two structural findings phase 2 should design against:

1. **The prompt cache survived process death *and* the fork.** The channel exited at 03:49:10Z; a *different* process, resuming into a *different* child session id, hit the same cached prefix at 03:55:18Z and paid warm rates. Prefix-cache residency is bound to the **bytes**, not to the process and not to the session id. This is load-bearing for the always-warm intercom design — warmth is a property of the prefix, so a channel that dies does not necessarily cost a cold restart.
2. **Writes land in the `ephemeral_1h` bucket, not `ephemeral_5m`** — every cache write across all three runs. The 6 min 23 s gap observed here is a **lower bound** on residency and nowhere near a test of the ceiling.

**Warning for phase 2's cold baseline: it must start from a genuinely cold prefix.** Neither the $1.59 nor the $0.233 figure is cold, and the $4.26 figure is cold only for the vehicle prefix as it stood on 26-07-28.
