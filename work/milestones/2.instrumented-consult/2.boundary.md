# Phase 2 — boundary: close the false clean sheet

## Objective

Reconcile `consult`'s DENY list against the live v2.1.220 tool registry, and — using the event parser phase 1 built — turn M1's `permission_denials` trap into an enforced invariant: a consult that successfully used a tool outside the read-only allowlist says so, loudly, instead of reporting a clean sheet.

Rated `medium` despite being small: this is the security boundary, the guard predicate has genuine false-positive design in it, and one of the four tools needs an empirical probe rather than a decision.

## Scope

### The DENY reconciliation

M1's audit found **no stale names** — all 31 existing entries live in 2.1.220 — and **three uncovered tools**: `SendUserMessage` and `ListAgents` (message class) and `ReadMcpResourceDirTool`. Add them.

**`Cd` is a fourth candidate and must be probed before it is added.** M1 rated it lower-confidence, escape-class. Establish whether it is a live tool name in 2.1.220 and whether it is reachable from a session under this construction; add it if so, and **record the probe's result either way** — a name added on speculation is as much a maintenance liability as one omitted.

**Restate the structural limitation; do not attempt to fix it.** The hazard is that the harness's deferred/built-in tool class is *name-deny-only* — `--allowedTools` does not default-deny it — so DENY must be a complete superset rather than a backstop, and every harness upgrade can silently reopen the boundary. Reconciling the list does not change that. `.claude/ADR.md`'s entry is updated to describe the reconciled state **and** to keep the limitation stated, with the audited version bumped from 2.1.197 to 2.1.220.

### The guard

**The signal is not `permission_denials`.** M1 measured it reporting `[]` across all five `result` events of a session that had genuinely refused two tools — an auditor trusting it reads a clean sheet on a session that was actively blocking. The real evidence is the `user`/`tool_result` event carrying `is_error`.

The guard's question is narrow and positive: **did any tool outside `Read`/`Grep`/`Glob` execute successfully?** A refused attempt is the boundary *working* and must not trip it — M1's channel emitted `tool_use` for `Write` and `Bash` and was correctly refused, which is the expected shape, not a violation.

On detection: **warn loudly on stderr, exit non-zero, still return the answer** (operator ruling 3). Not a hard-fail — a parser false positive must not destroy a legitimate answer, and the operator explicitly weighed that trade.

### The fixture

The guard must be provable without staging an actual boundary breach. Build a small fixture of recorded events under the milestone directory — one clean transcript excerpt, one synthesised excerpt carrying a *successful* out-of-allowlist `tool_use`/`tool_result` pair — and assert the predicate against both. That is what makes this phase headlessly certifiable rather than a claim.

### Hardened at the Reconnaissance gate (26-07-29) — settled, not open

1. **The guard predicate is a conjunction**: the tool's name is outside `{Read, Grep, Glob}` **and** its `tool_result` has `is_error` falsy (absent *or* `false`). Never `is_error` alone — a successful allowlisted `Read` also has no error, and a guard keyed on the error field alone would flag it.
2. **The tool name comes from the join, not the result.** `tool_result` carries `tool_use_id`, not a name; phase 1 builds and exposes the correlation back to the originating `tool_use` block (phase 1 gate item 3). Consume it — do not build a second parser (acceptance item 6).
3. **Scan every `tool_result` event in the stream, not the terminal `result` event.** M1 never established that `result` carries a rollup of tool successes, and its one candidate field — `permission_denials` — is exactly the unreliable signal this phase exists to stop trusting. A guard keyed on `result` would miss violations entirely.
4. **A dangling `tool_use` with no matching `tool_result` does not trip the guard.** There is no positive evidence of success, and operator ruling 3 makes this phase false-positive-averse. Document the choice in a comment rather than leaving it implicit.
5. **MCP and subagent tool names are moot under this construction, and say so.** `--strict-mcp-config --mcp-config '{"mcpServers":{}}'` means no `mcp__*` name can appear, and `Task`/`Agent`/`Workflow` are already denied, so no nested tool use is reachable. A one-line comment keeps a future reader from wondering why neither is handled — it is an assumption being relied on, not an oversight.
6. **Exit code 5** — `boundary violation detected; answer returned` (operator ruling). Add it to the header's documented ladder and to `work/PROJECT.md`'s smoke-test description in the same commit. It must be distinct: reusing 1 would make "you called me wrong" indistinguishable from "the read-only boundary was breached."
7. **The ADR stays version-free** (operator ruling, correcting this doc). The hazard entry keeps pointing at the pin in the script's comment rather than duplicating it — the version-free-canon discipline of missions v2 and v3, and one source of truth instead of two that drift. **The bump from `2.1.197` to `2.1.220` happens in `.claude/bin/consult`'s header comment only.** The entry's body prose does not change; the structural limitation must survive intact.
8. **Three fixtures, not two** — `clean`, `refused`, `violation` — since acceptance items 4 and 5 are separate demonstrations. Newline-delimited JSON (`.jsonl`), so they exercise phase 1's real parser rather than a second one. **Seed material exists for two of the three**: M1's `tmp/spike/*.stream.jsonl` files are still on disk (gitignored) and carry real clean turns and both genuine refusals with verbatim `tool_use_error` text — copy and trim into the fixtures directory as tracked content, never reference `tmp/` in place. The **violation fixture must be synthesised**: no successful out-of-allowlist call has ever been recorded here, because the boundary held in both real probes.
9. **The proof runs from a committed runner script** beside the fixtures (operator ruling), following M1's apparatus precedent — under the milestone directory, archiving with the mission, never entering `.claude/`. Production tooling stays free of test logic.
10. **The `Cd` probe may return a third shape, and that is a valid result.** Static extraction against the 2.1.220 binary found `filePatternTools:[…,"Cd"]` plus `validateCdTarget`, `handleSetCwdControlRequest`, `cdRuleRefusalMessage`, and `relocateSession` — a real implemented tool with **its own refusal-message path, distinct from the generic "exists but is not enabled" text** the other denied tools produce. That hints `Cd` sits behind a separate rule surface rather than the deny-by-name mechanism. If the probe finds "callable but self-refusing regardless of DENY," record that shape rather than forcing it into add-or-reject.

### Added at the phase-1 gate (26-07-29) — the ordering invariant

Phase 1's review found `degrade()` exits synchronously with the usage render ordered *after* every call site, so a consult that burned tokens and then failed reported no cost. **The guard has the identical shape**, and the mission architect confirmed the exposure is real and ruled the tightening within this phase's existing intent, not a new decision: ruling 3 already requires the warning to fire; this makes "fires" true on failure paths and verifiable.

Why it matters more here than for cost: the guard **is** D5's enforcement. If any exit path can skip it, the boundary is enforced only on the paths where nothing went wrong — enforcement theater. And a violation-plus-wire-failure is a *more* likely violation shape than one that misbehaves and completes cleanly.

- **Prefer a structural fix over call-site ordering.** Phase 1's hoist was correct but is the fragile shape — every future exit path re-creates the bug. Route all exits through **one finalizer** (a choke point that flushes accounting and the boundary verdict), so ordering is a property of the code's structure rather than of each call site's discipline.
- **A fourth fixture: `violation-truncated`** — a stream carrying a successful out-of-allowlist pair, then terminating mid-stream as a wire failure would leave it. This also covers the ENOBUFS shape phase 1 corrected: on bun 1.3.14 `spawnSync` **returns** with `run.error` set and `status: 143` rather than throwing, so failure arrives through normal control flow and a try/catch-shaped guard placement would miss the real failure shape entirely.
- **Exit-code precedence, settled by the Executor at the gate** (control-flow semantics inside the ruled framework): the warning is the invariant channel and **always** precedes exit. Exit **5** when an answer was returned. When degrading — no answer to return — **degrade's own code stands, with the warning already emitted**. Both signals preserved, neither overloaded.
