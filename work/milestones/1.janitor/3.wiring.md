# Phase 3 — wiring: the hat at every boundary

## Objective

Wire the competency into the workflow's existing chokepoints so hygiene is enforced by the normal path (milestone P3) — prevention at plan time, an advisory sweep at order close, a blocking pass at milestone close. Seven surgical edits, no new machinery: the Blessing gate is already the plan-time chokepoint every work order passes.

Design is settled; this phase is precision prose against known anchors. Line numbers below are as surveyed 26-07-25 — verify before editing, they will have shifted.

## Scope

**1. Prevention — the blessing hygiene lens.**

- `.claude/agents/architect/CLAUDE.md` § Blessing duty (~line 15): the blessing judgment gains a hygiene lens — does this order, as planned, **state where its artifacts land**, consistent with the project's declaration? A plan that does not say is critiqued for it; a plan that says something the declaration contradicts is a directive, and if the contradiction is a genuine structural fork it escalates to the operator like any other new design decision.
- `.claude/agents/manager/CLAUDE.md` § Architect Blessing (~lines 64–71): the submitted order is expected to carry the statement; note the lens among what the Architect reads for.

**2. Prevention — the required *where-artifacts-land* statement.** Three planning-artifact shapes gain it:

- `.claude/agents/architect/workflows/plan-milestone.md` step 5, as a new phase-decomposition discipline bullet (after the operator-gates bullet).
- `.claude/agents/manager/workflows/plan-work-order.md` — the `## Implementation Plan` / `## Resolution Plan` / `## Refactor Plan` sections in the type-polymorphic document-structure block. These currently carry only a one-line parenthetical; add the requirement without inventing an elaborate sub-shape — one stated sentence naming new paths and their declared home is the bar.
- `work/milestones/README.md` § Conventions — the phase-doc shape line, so the requirement is canon at the scaffold level and not only in the workflow that authors it.

The bar is deliberately low: **any plan that creates files says where they go and against which declared category**. It is a sentence, not a section.

**3. Enforcement — the advisory order-close checklist.**

- `.claude/agents/manager/CLAUDE.md` § Closing Out (~lines 145–157) and `.claude/agents/manager/workflows/execute-work-order.md` steps 15–20: the Manager wears the hat for a **light, explicitly advisory** check — did this order leave the tree consistent with the parts of the declaration it touched? Findings above the mechanical threshold are noted or filed; they never block the close.
- The rationale must be stated where the checklist lives, because a reader will otherwise ask why this one is advisory: **whole-repo drift is invisible at order scale** (fork 4 resolution) — blocking here would tax every order for drift it cannot see.
- Placement: before the commit step, since the automatic-mode verdict is written after the close-out commits land.

**4. Enforcement — the blocking milestone-close pass.**

- `.claude/agents/executor/workflows/execute-milestone.md` step 8 (Objective close): insert the pass between "all phases reach acceptance" and the close-out actions. The Executor wears the hat and runs the **full pass, blocking**: the milestone does not close until the pass runs clean or its contestable findings are explicitly escalated. In automatic mode an unresolved rung-3 fork is an **ESCALATE halt**, mirroring the Blessing gate's semantics (`execute-work-order-automatically.md` § Acceptance Verdict is the vocabulary's home — reference it, do not redefine it).
- `.claude/agents/executor/CLAUDE.md`: mirror the duty wherever that doc enumerates the Executor's close responsibilities, so the two do not drift.

**5. Record — `.claude/ADR.md`.** One entry: the Janitor as staff competency worn as a hat; the declaredness + reconciliation floor; the gate semantics (advisory at order scale, blocking at milestone scale) and why they differ. Cite the enacting mission and the proposal.

**6. `/initialize` reach.** If phase 1's BASELINE § Expectations edit did not already cover it, ensure the audit's keystone-docs or scaffold check notes that `work/PROJECT.md § Structure` is expected. `/initialize` stays read-only and reports; it does not run the pass.

**7. The child-collection rule — added post-planning by charter amendment A3 (26-07-25), an eighth edit site.** Evidence and rationale live in `work/MISSION.md` § Amendments A3 (fourth in-anger instance of v1's verdict-absence trigger, this campaign's phase 1). The rule, stated **once** in `.claude/agents/manager/CLAUDE.md` (turn-discipline/closing territory) and referenced — never re-worded — from the terminal steps of both `execute-work-order.md` and `execute-work-order-automatically.md`:

> A Manager's turn may not end between dispatch and collection. Dispatch is never completion; the only legitimate turn-ends are the `## Acceptance Verdict`, a pause-and-ask question, or an explicit ESCALATE. Collect every dispatched child — result received and folded into the work doc — before ending a turn.

State the topology rationale where the rule lives: a child's report travels only by collection (a depth-2 agent cannot address its parent by name), so an uncollected child's report strands upward to whoever is active. Cross-reference in `.claude/agents/executor/CLAUDE.md` where the topology limit is already documented: the rule is the *prevention*; the Executor's SendMessage nudge remains the *recovery* when it is breached.
