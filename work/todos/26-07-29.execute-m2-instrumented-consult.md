## Reconnaissance

> executor@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

Two researcher subagents, read-only, parallel. Both earned their keep: one found a contradiction inside a phase doc written the same evening, the other found an implementation detail whose absence would have produced a guard that cannot work.

### Defects in the plan as written

**W-1 — "No file writes" collides with the oversized-answer fallback.** Phase 1's output-contract section states operator ruling 2 as "no file writes, no evidence-note append, no repo-specific paths," and four paragraphs later requires the oversized-answer fallback to *write the answer to a file and return the path*. Ruling 2's actual target is auto-appending usage to the evidence note, not file writes in general — so they are not truly contradictory, but a literal-minded implementer stalls here. The phrasing must be narrowed to what was ruled.

**B-1 — `tool_result` does not self-report the tool name.** The guard's whole question is "did a tool *outside* `Read`/`Grep`/`Glob` execute successfully" — but a `tool_result` event carries `tool_use_id`, not a name. The guard must **join back** to the originating `tool_use` block by id to learn what ran. Phase 2 waves at this with "reuses phase 1's parser" without establishing that phase 1's parser retains the mapping. **It must**, and that is now a phase 1 requirement, not a phase 2 discovery.

**B-2 — No exit code fits a detected violation.** Phase 1 is instructed to *preserve* the 0/1/2/3/4 contract; phase 2 then requires "non-zero exit" for a violation that still returns its answer. Reusing `1` collides with usage/unparseable-handle. This needs a new code — a contract *extension* layered on a preserve instruction, which is a decision, not an implementation detail.

**B-3 — The ADR carries no version number, by design.** The hazard entry deliberately points at "the pinned version in the script's comment" rather than duplicating it — the version-free-canon discipline missions v2 and v3 established. Phase 2 says to bump the audited version *in the ADR entry*, which would break that precedent.

### Risks and unknowns

**The error-subtype branch has no empirical basis.** Phase 1's failure rework keys on "no terminal `result` event, or one with an error subtype" — but across M1's entire spike, **every** `result` event carried `subtype: "success"`, including both boundary-probe refusals. No error subtype was ever observed. Worse, **what a nonexistent `--resume` id emits under stream-json is entirely unknown** — M1 always used a valid vehicle. The current empty-stdout heuristic exists precisely because a child can fail to resume even when the file exists (stale cache, mid-write race). This is the phase's self-declared "subtle part" resting on an untested assumption; it wants one throwaway probe before the branch is written.

**`permission_denials` is a trap for phase 1 too.** M1 scoped it to the boundary guard, but it is a natural thing to reach for once you are already parsing `result` — and a phase 1 that used it as a "did this run cleanly" signal would silently reproduce the exact false-clean-sheet defect M2 exists to fix. Phase 1 must not touch the field at all.

**No test runner exists in this repo.** Four bin scripts, no `scripts` field, no `bun test`, no `*.test.ts`, no fixture convention anywhere. Phase 2's "proven against the fixture" has no precedented mechanism to invoke.

**`spawnSync` ENOBUFS may throw rather than set `.status`.** The current code branches on `run.status !== 0` and never wraps the call; stream-json is a genuinely different volume profile even if 64 MB is unlikely to be approached. Worth an explicit check rather than an assumption carried from plain-text days.

**Cross-boundary reuse is impossible, and that is correct.** `work/milestones/1.spike/harness/channel.ts` parses this exact wire — but `work/` archives into `work/missions/<v>/` and vanishes, while `.claude/bin/consult` must run standalone in a bootstrapped copy that never had the harness. No import is available; hand-porting the small parsing/trap logic with attribution is the lower-risk path over reimplementing from prose. Copying the harness's async spawn machinery would be actively harmful — `consult` is single-shot and its `spawnSync` shape is structurally correct.

### Findings that strengthen the plan

**All four M1 traps verified accurate**, with one understatement worth carrying: `usage.iterations[]` does not merely lack detail — it holds a **single entry containing only the last model call's usage** (562 aggregate against 450 in the sole iteration; 376 against 136). A naive read silently under-reports cost by exactly the earlier iterations' worth.

**No caller needs editing.** Every live `consult` call site reads stdout as prose; two (`manager/CLAUDE.md:68`, `:126`) branch on failure to reach a documented degrade path. Since stdout stays answer-only, the entire risk surface is whether the failure rework preserves the exit-code contract — not whether callers change. None do.

**`Cd`'s static evidence is far stronger than M1 had.** Extraction against the 2.1.220 binary found `filePatternTools:["Read","Write","Edit","Glob","NotebookRead","NotebookEdit","Cd"]` plus a cluster — `validateCdTarget`, `handleSetCwdControlRequest`, `cdRuleRefusalMessage`, `relocateSession`. It is a real, implemented tool with its own validation and, notably, **its own refusal-message path distinct from the generic "not enabled" text** the other denied tools produce. That hints `Cd` may sit behind a separate rule surface rather than the deny-by-name mechanism — meaning the probe may return a *third* shape ("callable but self-refusing regardless of DENY") that the phase's binary add-or-reject framing does not accommodate.

**`ReadMcpResourceDirTool` independently confirmed** — it appears by name in a live 2.1.220 session's own deferred-tool listing, corroborating M1's finding from a second observation. No further missing names found: cross-checking DENY against a live 21-name deferred listing, every one is present except that tool.

**Fixture seed material exists for two of three cases.** M1's `tmp/spike/*.stream.jsonl` files are still on disk (gitignored) and carry real clean turns *and* the two genuine refusals with verbatim `tool_use_error` text. Only the violation excerpt — a *successful* out-of-allowlist call — must be synthesised, because the boundary held in both real probes and no such event has ever been recorded here.

Four options were put to the operator. The Executor recommended, and the Manager independently reached, a fourth not in the Manager's original three: tighten `DENY` to strip `Skill` and `ToolSearch`, treating the over-broad *grant* as the defect rather than arguing about where the guard's line falls. **The operator ruled otherwise: widen the allowlist to all six granted names.** The ruling stands and is implemented.

The trade-off is real and is therefore written into the deliverable rather than left in this log: under this ruling the guard's allowlist *is* a description of whatever the harness currently grants, so it drifts on every harness upgrade, and a future version granting a mutating tool would widen the boundary silently. Three bindings follow — a comment at the allowlist naming it a deliberate ruling with a re-enumerate-on-upgrade instruction; a second surface on the ADR's DENY-drift hazard entry, kept version-free per the earlier ruling; and the granted-set correction carried into the phase doc addendum, since it corrects a premise both phase docs and the ADR entry held.
