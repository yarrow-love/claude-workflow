# Phase 1 — wire: read the event stream, report the cost

## Feature Request

> executor@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

Seeded from [`work/milestones/2.instrumented-consult/1.wire.md`](../milestones/2.instrumented-consult/1.wire.md), which stays the spec and the record — **read it in full before planning**, including its § Hardened at the Reconnaissance gate block. Campaign log: [`26-07-29.execute-m2-instrumented-consult.md`](26-07-29.execute-m2-instrumented-consult.md).

**The objective.** Convert `.claude/bin/consult` from capturing child stdout as an opaque string to parsing a `--output-format stream-json` event wire — extracting the answer and per-consult `usage` — without changing what any existing caller sees on stdout.

**The specification already exists.** `work/milestones/1.spike/1.channel.md` § Addendum maps this wire and names four traps. M2 needs no new measurement; it needs careful implementation against established fact.

**The consult handle.** The last `architect@…` entry above is the milestone architect. It is the same session as the campaign Executor — this milestone was planned and is being executed in one flagship session. Consult it for plan-interpretation questions via `.claude/bin/consult`; genuinely new design decisions escalate.

### The three things most likely to be got wrong

1. **Failure detection, not usage capture, is the hard part.** The current empty-stdout heuristic dies under stream-json. Rekey it on the terminal `result` event — but **probe first**: across M1's whole spike every `result` carried `subtype: "success"`, so the error-subtype branch has no empirical basis, and a bogus `--resume` under stream-json is untested. One throwaway probe, then write the branch against what you saw.
2. **Build the `tool_use_id` → tool-name mapping.** Phase 2's guard depends on it and cannot build its own parser. `tool_result` events carry only the id.
3. **Never touch `permission_denials`.** M1 measured it reporting `[]` across a session that genuinely refused two tools. Reaching for it as a "ran cleanly" signal reproduces the exact defect this milestone exists to fix.

## Research Findings

> manager@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

Distilled from one researcher dispatch. Environment: `claude` 2.1.220, `bun` 1.3.14, `jq` 1.8.2 — matching M1's recorded baseline.

**The probe ran, and it overturns the pessimistic assumption** (gate item 4 / acceptance 13). A bogus `--resume` under `--output-format stream-json --verbose` exits **1**, prints `No conversation found with session ID: <uuid>` on stderr, and emits **exactly one line on stdout** — a terminal `result` event:

```
{"type":"result","subtype":"error_during_execution","is_error":true,"num_turns":0,
 "duration_ms":0,"total_cost_usd":0,"usage":{…all-zero…},"permission_denials":[],
 "errors":["No conversation found with session ID: 00000000-0000-4000-8000-000000000000"]}
```

So the error branch has empirical basis after all: `subtype: "error_during_execution"`, `is_error: true`, and an `errors[]` array carrying the same text as stderr. The failure branch is written against *this*, not against a guess — and it means both failure shapes are real and must be handled: **no `result` event at all** (process died before completing) and **a `result` event with `is_error`/non-`success` subtype**.

**The happy path, confirmed on a real archived handle** (`c256e59e-…`, the smallest local transcript). Event sequence: `system`(subtype `init`) → `assistant` → `rate_limit_event` → `result`. Four lines. The answer is `result.result` (a plain string); `result.usage` carries every field acceptance criterion 3 names — `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, and nested `cache_creation.{ephemeral_5m,ephemeral_1h}_input_tokens` — plus `total_cost_usd` at the event's top level. M1's wire map holds; no discrepancy to record.

Note `rate_limit_event` — an event type M1 did not enumerate. The parser must tolerate unknown types rather than switch exhaustively.

**`--verbose` is not required on 2.1.220.** The researcher re-ran the probe without it and got an identical single-line `result`; the CLI did not reject `-p --output-format stream-json` alone. It is retained anyway — acceptance criterion 1 mandates its presence, the Executor's own recipe carries it, and older versions did require it. Recorded as a finding, not acted on.

**Nothing exists to port for the `tool_use_id` mapping.** `work/milestones/1.spike/harness/channel.ts` does no event-type discrimination at all — it `JSON.parse`s each line into an untyped `Record<string, any>` and hands consumers a `waitFor(pred)` API. The extraction helpers live in the sibling `spike-run.ts`: `assistantTextIn()` walks `assistant` → `message.content[]` for `{type:"text"}` blocks, and `toolUsesIn()` walks the same path for `{type:"tool_use"}` blocks but **discards the block's `id`**, returning bare names. Grep across the whole spike tree found no id-keyed map. Phase 1's correlation deliverable (acceptance 12) is therefore built from scratch: walk `assistant` events' `message.content[]` for `{type:"tool_use", id, name}` and key a map by `id`, so a later `tool_result` (which carries only `tool_use_id`) resolves to a name.

**What ports, then, is small**: the answer-from-`result.result` convention, the `assistant`-content-block walk, and the trap discipline (`result.usage` over summed `assistant.message.usage`). The async `Bun.spawn` / held-open-stdin machinery is explicitly out of scope — `consult` stays single-shot `spawnSync`.

## Implementation Plan

> manager@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

**Shape: one implementation phase, then one verification phase — strictly sequential.** The planner argued against splitting and I accept the argument: every part of the change converges on the same tail region of one 243-line file, and any intermediate state (flags added, parser absent) puts raw JSON lines on stdout and breaks every existing caller. Two implementers on one file is also the file-transfer hazard (`.claude/ADR.md` § Standing hazards). One implementer, one phase, one commit.

### Phase 1 — rewire `.claude/bin/consult` onto the event wire

In place; no new files. Nine steps.

1. **Command array** — insert `--output-format stream-json --verbose` immediately after `--fork-session`. Both are non-variadic, so they are safe there; `--permission-mode dontAsk` stays last before the prompt because the variadic list flags would swallow a trailing positional. `--model fable` untouched. A comment records that `--verbose` is *not* required on the pinned CLI but is retained deliberately.
2. **`--usage-json` argument** — parsed, added to the `positional` filter predicate (the easy thing to forget: unfiltered it lands as the handle or the question), and added to the usage string.
3. **The parser block**, placed *below* the `--dry` early exit — so `--dry` is unaffected by construction, not by discipline. One entry point `parseWire(raw)` returning one record: `{events, result, answer, usage, costUsd, toolNames, toolResults, unparsedLines}`. Lines are `JSON.parse`d in a `try`/`catch` counting failures rather than throwing; **unknown event types are retained and ignored, never switched on exhaustively** — the observed stream carries `rate_limit_event`, which M1 never enumerated. Attribution comment per gate ruling 9, worded **without a mission-tree path** (that path is not scaffold-invariant and would fail acceptance 10 while decaying at archive time).
4. **The `tool_use_id` map** — built by walking **content blocks, not event types**: any event with an array `message.content` contributes `{type:"tool_use", id, name}` to the map and `{type:"tool_result", tool_use_id, is_error}` to the results list. Content-driven precisely because the carrier event type for `tool_result` was never enumerated by M1, and assuming it is a `user` event would be the untested assumption gate ruling 4 forbids. Comment marks it as phase 2's consumption point.
5. **Spawn + the ENOBUFS guard** — `maxBuffer` stays 64 MB with a comment recording it was re-examined and found adequate (the wire's overhead is additive per-event framing, not a multiplier on answer length). The missing guard is added in **both** forms: a `try`/`catch` around `spawnSync` for the throw, and a `run.error` check for the error-object form. Both print loudly and exit 3.
6. **Answer emission + the oversized fallback** — threshold `ANSWER_MAX_BYTES = 256 * 1024`; beyond it the answer is written to `os.tmpdir()` (never a repo-relative path — gate ruling 2) and the path returned as the message, with a loud stderr note naming the threshold and the fallback framing. Below it, the answer goes to stdout verbatim with a trailing newline normalized in.
7. **Failure detection, rekeyed** — mapping below.
8. **Usage rendering on stderr** — a compact human line by default, or (with `--usage-json`) a single JSON object *instead*, always the last stderr line by construction. Raw field names verbatim.
9. **JSDoc header** — updated for the wire, the output contract, the fallback and the reworded exit 3. **Hazard**: a literal comment-close sequence inside the header makes bun refuse to parse the file (`.claude/ADR.md` § Standing hazards) — verify with `bun .claude/bin/consult` immediately after editing it, before anything else.

**Cost as a delta (trap 1)** — real arithmetic, not a comment decorating an identity:

```ts
const prev = resultEvents.length > 1 ? num(resultEvents.at(-2)!.total_cost_usd) : 0;
const cost = num(resultEvents.at(-1)?.total_cost_usd) - prev;
```

A single-turn consult has one `result`, so `prev` is 0 and the delta is the whole value — but a future multi-turn caller inherits the right number without editing the code.

**The four trap comments** each open with the literal token `Trap 1 —` … `Trap 4 —`, so `grep -nE "Trap [1-4]"` returns exactly four hits (acceptance 6's verification). Sites: trap 1 at the delta arithmetic; trap 2 at the parse preamble (nothing keys on `system`/`init` or assumes its uniqueness); trap 3 at the assistant-text walk and the usage read (the walk is for **text only** and joins rather than sums); trap 4 beside the usage field picks (`iterations[]` deliberately not read).

**The prohibition is grep-verifiable in both directions.** `permission_denials` must appear nowhere in the file **including comments** — the natural instinct is to write "we deliberately do not read `permission_denials`", and that comment itself fails acceptance 14. Any note is phrased without the token.

**Failure detection — the new discriminant.** The exit-code contract is preserved exactly (`0` ran/dry · `1` usage/unparseable handle · `2` cross-machine · `3` transcript unusable · `4` repo mismatch · `5` unused, reserved for phase 2). Only the mapping changes:

| Observed condition | Exit |
| --- | --- |
| `spawnSync` threw, or `run.error` set (ENOBUFS either form, ENOENT) | 3 |
| `wire.result === null` — no terminal `result` event anywhere | 3 |
| `wire.result.is_error === true` or `subtype !== "success"` — **the observed bogus-`--resume` shape** | 3 |
| terminal `result` present and successful, but the answer is empty after the assistant-text fallback | 3 |
| child `run.status !== 0` with none of the above (wire/CLI disagreement — not papered over) | 3, after emitting whatever answer exists |
| all clear | 0 |

`errors[]` is used for **message text only, never control flow** — the discriminant is `is_error`/`subtype`; `errors[]` is echoed to our stderr so the reason survives when a caller redirects the child's inherited stderr away.

**The branch cites the probe *abridged*, not verbatim** (Blessing directive 1). The observed `result` line contains the forbidden field name, and acceptance 14's grep covers comments — so a verbatim citation in code would fail V6 against acceptance 14. The comment carries the **shape**: the subtype, `is_error`, the `errors[]` text, with untouched fields elided by `…`. The verbatim transcript stays in this document's § Research Findings, which is what acceptance 13's "its output is recorded" actually asks for. Code cites the shape; the doc holds the transcript.

**`.claude/BASELINE.md` needs no edit** — verified, not assumed: it names `consult` at lines 29/31/35 and enumerates no argument surface for any script (`--dry` and `--model` appear nowhere in it), so `--usage-json` changes nothing it asserts. The milestone's same-commit condition is not triggered.

## Code Review

> reviewer@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

One fresh reviewer pass over the whole diff, then a manager re-evaluation against the acceptance criteria directly. **One blocking finding, mechanical, resolved; two non-blocking nits, folded into the same pass. No design finding — nothing reopened, so no escalation.**

**Blocking — usage was lost on exactly the degrade paths that had usage to report.** `degrade()` ends in `process.exit(3)`, which is synchronous, and the usage-render block sat *after* every call site. The plan's step 7 renders usage "only when `wire.result` exists — so an error result still reports its zeroed usage", which splits the three degrade sites cleanly: `wire.result === null` was **correct as-is** (no result event, nothing to report), but the `is_error`/bad-subtype and empty-answer-despite-success sites both *have* a `wire.result` carrying a real, possibly non-zero `usage` — and reported nothing. A consult that burns cache-creation tokens and then fails on the wire was silently costing money it never accounted for. In a milestone whose entire purpose is instrumenting consult cost, that is the defect landing squarely on the objective, not a pedantic one.

**Resolved** by hoisting the render into a `renderUsage(w)` arrow above `degrade`, and having `degrade(why, w)` call it when a wire with a result is present. Verified against a stub `claude` emitting an `is_error` result with non-zero usage: exit stays 3, the usage line now appears and is still the **last** stderr write, and `--usage-json` still suppresses the human line and leaves stdout empty. The `wire.result === null` site deliberately still passes no wire, so it renders nothing — the plan's gating preserved exactly.

**Non-blocking, both folded in.** The header's exit-3 prose did not cover the "wire reported success but the child exited non-zero" branch, where an answer *has* already reached stdout — reworded. And the spawn-failure branch hand-duplicated `degrade`'s message text, so it was the one failure path missing the `--model fable` retry hint — routed through the shared helper, keeping the errno detail that makes it diagnosable.

**Clean on every other axis the review checked**: the four grep invariants; each trap comment's siting *and* content (a correctly-numbered comment saying the wrong thing would still defeat acceptance 6's purpose); the cost delta as real arithmetic over ordered `result` events rather than an identity dressed in a comment; parser robustness (no exhaustive `type` switch, parse failures counted not thrown, the `tool_use_id` map built from content blocks); flag ordering with `--permission-mode` still last and the five-layer read-only boundary untouched — the diff contains no `DENY` line at all; `--dry` isolation below the early exit with all helpers `const` arrows; `--usage-json` filtered out of `positional`; and all seven decision points implemented as blessed.

**Statements the criteria require in this document** (plan V8):

- **(5)** Cost is a delta over the ordered `result` events, not the cumulative process total. A single-turn consult has one `result`, so the delta *is* the whole value — written as a delta anyway so a future multi-turn caller inherits the right number without editing the code.
