## Reconnaissance findings carried in

Established empirically at the gate (bun 1.3.14, this host) — **do not re-probe these, build on them**:

- **`spawnSync` honors `timeout`.** A `sleep 10` bounded at 1000 ms returned at 1006 ms with `status: null`, `signal: "SIGKILL"`, `error.code: "ETIMEDOUT"`. **There is no `status: 143`** — key the `timed_out` branch on `error.code`/`signal`, never on a status number.
- **Detached spawn survives parent exit.** A detached child kept writing for ~6 s after its parent exited. `stdio: "ignore"` is load-bearing, not cosmetic: inherited stdio keeps the parent's event loop alive.
- **`process.kill(pid, 0)`** throws `ESRCH` on a dead pid, silent on a live one. **`fs.openSync(path, "wx")`** throws `EEXIST`. `process.execPath` is the bun binary.
- **`--usage-json` goes to stderr** as its guaranteed-last line, and is emitted **independent of exit code** — see the emission matrix in the phase doc § Telemetry. The rate-limited case emits usage on **exit 3**. Never gate usage parsing on exit 0.
- **`consult:516-526`'s spawn idiom is directly reusable** (the `try`/`catch` *plus* `run?.error` double-check), needing only `timeout`/`killSignal` added.
- **The `rate_limit_events` addition is one line** at the usage-object literal (`consult:391-400`); `renderUsage` spreads that object, so the render site needs no edit and the human-readable line stays byte-identical.
- **Nothing in `.claude/bin/` has ever done detach, locking or liveness** — the daemon mechanics are new territory, de-risked only by the probes above.

### Decision points

Ten were surfaced; the six above plus: one short-lived lock per critical section rather than a daemon-lifetime lock; lapse as a computed predicate with a `lapsedAt` stamp written at the transition (pure computation either spams `lapsed` every tick or never records it); per-handle cadence stored in the handle file (a global daemon flag cannot express the smoke test's `--interval 60s` without a restart); a short daemon wake quantum for heartbeat freshness with `tick` invoked only at next-due (sleep-a-full-interval makes criterion 17's worst case 58 minutes).

### Manager rulings on the planner's five open questions

## Code Review

> reviewer@play/a3117b31-b7e0-4a55-bc48-fc6a0a163214

Two independent passes, both fresh dispatches escalated to opus for the concurrency surface. Both reviewers reproduced their findings behaviorally against stubs rather than reasoning from the code alone, which is why the list below is short on opinion and long on evidence.

**Pass 1 — 8 findings, 1 blocking, all mechanical.** The blocking one was a genuine defect the build's own verification had missed: `tickPass` snapshots the registry and `beat` re-writes the entry file when `consult` returns, while `release` unlinked with no coordination — so a release issued during that handle's beat printed `released:` and was silently undone seconds later. The resurrected handle would then beat forever on real tokens with no error surfaced until the 18-hour dormancy bound caught it, and the daemon would never exit, breaking criterion 17 outright. The window is seconds wide and criterion 18's smoke procedure has exactly that shape, so the next phase would plausibly have hit it and recorded wrong evidence. Resolved by guarding every tick-path write on the entry still being registered, and by taking the lock in `release`.

The other seven: `stampLock` writing non-atomically and without an ownership check (a reaped holder could resurrect the lock under its own pid and silently disarm the new owner's release); the daemon's pidfile heartbeat refreshing only per wake while the lock refreshed per entry, so a long pass made a live daemon look dead; `stop` signalling an unverified pid; `readRegistry` not enforcing filename-to-body uuid agreement, which was the one way the tick path could write another handle's file; an fd leak on the lock's error path; a comment claiming a property the code lacked; and an unguarded dereference that threw out of `tick`.

**Pass 2 — 0 blocking. Converged.** All eight fixes verified sound, no regressions, and the reviewer's judgment on the one interaction the fixer had flagged for adjudication (a `stop` that defers rather than signalling a possibly-recycled pid) was that a stop-that-does-not-stop is the right trade: the failure is loud, recoverable by re-running, and unreachable at both the default and smoke cadences, whereas signalling an unverified pid is the one way this script can damage something outside its own domain.

Five non-blocking findings were reproduced anyway, and I took four of them with budget remaining, because two bore directly on the smoke test about to run:

- **The staleness bound was one constant doing two unrelated jobs.** Criterion 15 specifies 3× the beat interval for the *lock*; the daemon pidfile had simply inherited it, making a crashed daemon's pidfile look healthy for 174 minutes — or 2.9 hours on an empty registry. The reviewer reproduced the consequence: a 17-minute-stale pidfile whose pid had been recycled to an unrelated live process was judged healthy and `stop` killed the innocent process. Daemon liveness now bounds on what a live daemon actually guarantees (wake quantum and beat timeout, 210 s at default cadence); the lock's bound is untouched, and both the code and the header now say why the two differ.
- **The pass-1 `try`/`catch` had converted a crash into a token-burning loop** — the throw landed after the beat and before `lastBeatAt` was written, so dueness never advanced and every wake re-beat: seven real spawns in seven seconds on a malformed handle file. Closed at read-time validation, with `lastBeatAt` advancing in a `finally` as backstop.
- Nothing enforced `timeoutMs < 3 × intervalMs`, and violating it let a second `tick` reap a live tick's lock and beat the same handle concurrently. This **warns rather than rejects**: criterion 18's own prescribed cadence sits exactly on that boundary, so a guard that rejected it would reject the acceptance criterion's own command.
- `stillRegistered` was an existence check, so a release-then-re-register during an in-flight beat had the returning beat write its stale snapshot back — discarding the renewal's cadence flags and defeating criterion 4 in that window. It is an identity check on `renewedAt` now.

No finding in either pass reopened a design decision, so the post-review gate never fired.
