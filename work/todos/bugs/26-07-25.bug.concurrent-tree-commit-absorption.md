# Bug: a concurrent session's enumerated `git add` silently absorbs another session's uncommitted hunks

## Bug Report

> manager@play/9362ff9f-c270-4704-97cc-14d527ba9f12

**Symptom.** Two authorized sessions ran against the same working tree. The phase-4c build (this Manager) left `work/MISSION.md` and the `work/proposals/26-07-25.repo-hygiene.md` → `_enacted/` rename staged-but-uncommitted, per the workflow's manager-commits-at-close-out discipline. At 22:45:37 a separate mission-architect session committed `5d39307` ("Add: plan M2 return-path…") for its own charter-A4 reasons. That commit's file list carries:

```
work/MISSION.md                                    | 10 ++--
work/proposals/{ => _enacted}/26-07-25.repo-hygiene.md | 0
```

Both are phase-4c's work product. By the time phase-4c's own close-out ran, `git diff HEAD -- work/MISSION.md` was empty and the rename was already in `HEAD` — there was nothing left for the enactment commit to carry.

**Why the repo's own convention did not prevent it.** Root `CLAUDE.md` forbids `git add -A` / `git add .` and requires enumerated paths. Both sessions complied. Enumeration protects against sweeping up *unrelated* files; it gives no protection at all when a second session has pending hunks in the *same file* a first session legitimately needs to commit. `git add work/MISSION.md` is enumerated and still absorbs everything pending in that file.

**Consequence.** Content is correct; provenance is not. The phase-4c order instructed "repair them in the same commit" (`work/todos/26-07-25.prove-close.md:36`), and that instruction became unsatisfiable-as-written through no fault of either session's discipline. A close-out that wrote "link repair landed in the enactment commit" would have been false. Acceptance criterion 12's *substance* held; its commit-grouping form did not.

**Where found.** Surfaced by the fresh reviewer dispatched for phase-4c's review pass (finding 1, HIGH), confirmed by the Manager against `git show 5d39307 --stat` and `git log -- work/MISSION.md`.

**Not investigated, not resolved.** The candidate remedies the reviewer named — worktree isolation for concurrent sessions, or hunk-level staging discipline (`git add -p` / `git stash` boundaries) — are a design question, not a mechanical fix, and neither belongs to the order that found it.

**Note on adjacency.** This is a *tree-sharing* hazard, distinct from the return-path/collection hazard in `26-07-25.bug.orchestration-return-path.md`. Both are campaign-practice defects that only appear when more than one session is live; whether they want a common home is for whoever triages them.
