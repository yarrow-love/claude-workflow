# `/initialize`'s repo-indexed presence probe is unconditional, so a `None`-declaring repo nominal-FAILs with a repair that repairs nothing

> manager@play/2c481bc6-cd99-42ad-8395-48fe66481dbf

**Close-blocking for the mission.** Charter success criterion 7 requires `/initialize` green at enactment, and M2 phase 3 runs that gate. This cannot sit in the backlog.

## Symptom

`.claude/commands/initialize.md` item 2 states the repo-indexed check unconditionally: "the repo is indexed (`index_status` / `codebase-memory-mcp cli list_projects` — a presence probe only; **presence is not health**) — unindexed → report the index recipe from BASELINE.md".

On this repo, `list_projects` shows no row for `claude-workflow`, so a literal run reports **unindexed → run the index recipe** — a nominal FAIL whose named repair repairs nothing: `src/` holds a single `README.md` and `work/PROJECT.md` § Codebase graph declares `None`. The auditor avoided reporting the false failure only by importing judgment the check text does not supply, which violates the command's own governing frame (read-only; every failure names its fix).

## The asymmetry, and why it is not simply an `initialize.md` defect

Item 2 now carries **two** store/graph-dependent sub-checks and only one is conditioned on the seam declaration:

- **Wedge canary — conditioned, degrades gracefully**: "the store's wedge canary **where `work/PROJECT.md` § Codebase graph declares the store location**". On a `None`-declaring repo it correctly reads as inapplicable and says so.
- **Presence probe — unconditional**: no "when § Codebase graph declares an indexable surface" clause.

`.claude/BASELINE.md:81` **mirrors the same asymmetry**: it states the presence expectation bare ("the repo indexed — `codebase-memory-mcp cli index_repository --repo-path <repo>`") while conditioning store health "at the store location the consuming seam declares". So the defect is inherited from the declaring document, not authored by the auditing one.

## Where found

`.claude/commands/initialize.md` item 2 (line 8) and `.claude/BASELINE.md` line 81 — the matched pair.

## Why M1 phase 2 declined it (architect ruling, 26-07-27)

Routed to the milestone architect rather than settled. Ruling: **out of scope for phase 2, with mandatory routing.**

- **Not fixable in `initialize.md` alone.** A4's matched-pair discipline is not that step 2 audits *enough* — it is that BASELINE § Expectations and step 2 say the *same thing*. Conditioning the probe downstream only would land a knowing contradiction between the declaring and auditing documents: the whole-canon consistency failure caught by reading, never by a resolution probe. A pre-existing asymmetry made legible is evidence; a freshly manufactured declared-vs-audited mismatch would be a defect that phase authored.
- **Not fixable by releasing the BASELINE guard either.** The honest fix generalizes "the declaration governs applicability" from the store-location clause to **the graph expectation as a whole** — a `work/PROJECT.md` § Codebase graph declaring `None` switching the entire expectation off. That is a genuine extension of the audit contract for every consuming repo, i.e. **a new design decision**, which never resolves inside a blessing or a consult.

## The fix, and its venue

**The pair moves together**: both store-dependent clauses in *both* documents governed by the seam declaration, BASELINE and `initialize.md` in the same commit, symmetric.

**The applicability generalization is an operator decision at M2's `/plan`** — `/plan work/milestones/2.hazard-and-evidence` is an interactive operator dialog by construction, which is the designed venue. If anything forces the fix earlier than M2 hardening (e.g. an intervening `/initialize` consumer treating the nominal FAIL as blocking), that acceleration is the operator's call.

No investigation and no further resolution plan — the evidence above is the whole finding.
