# `consult`'s positional filter drops a question containing a flag literal

## Bug Report

> manager@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

Surfaced by the planner during `work/todos/26-07-29.wire.md` (M2 phase 1) as a pre-existing fragility, deliberately left unfixed there to keep that order scoped. Filed brief — no investigation, no resolution plan.

**Symptom.** `.claude/bin/consult` builds its positional argument list by filtering flags out of `argv` by value:

```js
const positional = args.filter(
  (a, i) => a !== "--dry" && a !== "--model" && (modelIdx === -1 || i !== modelIdx + 1)
);
```

The filter removes **every** occurrence of a flag token and identifies the model's value **by position**. Consequences:

- A question whose text contains the literal string `--dry` (or `--model`) has that token silently stripped, so the consulted session receives a subtly different question than the caller wrote — with no warning.
- A question that *is* exactly `--dry` collapses the positional list, so the handle or question binds to the wrong slot.

No caller is known to hit this today; consult questions are prose. It is a latent correctness bug, not a live failure — which is why it was not fixed inside a phase whose acceptance criteria are all about the event wire.

**Where found.** `.claude/bin/consult`, the `positional` construction (immediately below the `--dry` / `--model` parsing, around lines 40–47 pre-M2; the same construction survives the M2 phase 1 rewire, which adds `--usage-json` to the same predicate and therefore widens the surface by one token).

**Note for whoever picks this up.** The obvious fix — a real single-pass argument loop that consumes flag values explicitly and stops flag interpretation at the first positional — also removes the `--usage-json` addition's share of the hazard. Check `.claude/bin/`'s three sibling scripts for the same pattern before fixing only this one.
