# Phase 1 — probes: the decisive experiment battery

## Chore Objective

> executor@play/2cb889b5-b570-4b6d-b435-c315de40e68d

Establish the ground truth phase 2's doctrine rests on: a battery of falsifiable probes of the return-path topology, run on the pinned CLI through a probe-parent session that **is** the root observer (R2). Every verdict is behavior-based, quoted verbatim, and reproducible from its recipe. Spec: [`work/milestones/2.return-path/1.probes.md`](../milestones/2.return-path/1.probes.md); milestone: [`MILESTONE.md`](../milestones/2.return-path/MILESTONE.md); seeding evidence: [the filing](bugs/26-07-25.bug.orchestration-return-path.md) and [the proposal](../proposals/26-07-25.return-path.md).

**The hypothesis under test — H′, the liveness hypothesis.** The filing's original one-sentence theory was *"control descends edge by edge; every asynchronous return below the root collapses to the root."* Reconnaissance found that formulation overreaches its own evidence: every collapse in the filing's eight instances involved a dispatcher that **had stopped** (a turn ended mid-dispatch, or a continuation of a completed agent), while the M1 corpus contains a depth-1 dispatcher that stayed alive and *did* receive its background children's completions. The milestone architect ruled the refinement in (consult, 26-07-26) and restated the hypothesis this battery tests:

> **H′** — an asynchronous result is delivered to the dispatcher's own loop **if that loop is still live** when the result arrives; if the dispatcher has stopped, the result falls through to the nearest live loop above (observed: the root); and **no path exists for a stopped dispatcher to receive it afterward.**

The battery's job is to confirm, refine, or falsify H′ on the pinned CLI — and to exercise the idiom phase 2 would sanction, so that doctrine is never landed on an untested mechanism.

**What this phase does not do.** It does not design doctrine (R1 — phase 2, after `/plan`, with these verdicts as its only admissible evidence). It does not settle the reserved outcome (R4 — that escalates to the operator). It touches no canon (R3).

## Recipes

> executor@play/2cb889b5-b570-4b6d-b435-c315de40e68d

Each probe: **recipe → prediction → what would falsify it**. Evidence and verdict go in § Verdict record.

### P1-a — background dispatch, dispatcher stops *(the central claim, as chartered)*

Dispatch `subagent_type: researcher`, `run_in_background: false` (you collect this manager synchronously; the *manager's* child is the background one), `description: "probe-manager-1a"`, prompt:

> Dispatch a child agent with `run_in_background: true` and the prompt 'Reply with exactly: MARKER-P1A-CHILD'. As soon as the dispatch call returns — do not wait for the child, do not poll, do not sleep — end your turn with exactly: 'P1a: dispatched in background; ending turn.' Write no files. Run no git commands. Your entire output is your final message.

Then record, verbatim: **(a)** the manager's return and its captured `agentId`; **(b)** where the child's completion surfaces — a task-notification in your own root context (quote the whole block, including any `<output-file>` path and `<summary>`), your transcript, the manager's transcript, or nowhere; **(c)** after the child completes, SendMessage the manager by id: *"Did you ever receive your child's result? Quote verbatim whatever you received, or state that you received nothing."* — record its answer **and** independently check its transcript for the marker.

- **H′ predicts:** the completion surfaces at the root; the manager never receives it, before or after resume.
- **Falsifier (early exit):** the manager — having ended its turn — nevertheless received it. Then H′ is dead; record and stop per standing rule 10.

### P1-b — background dispatch, dispatcher stays alive *(the arm that separates the variables)*

Same dispatch shape, `description: "probe-manager-1b"`, prompt:

> Dispatch a child agent with `run_in_background: true` and the prompt 'Reply with exactly: MARKER-P1B-CHILD'. Then **stay alive**: do not end your turn. Poll by running short `sleep` commands in Bash (10 seconds each, up to 12 times), checking after each whether your child's result has arrived. The moment you receive it, quote it verbatim and end your turn with 'P1b: received: <the quote>'. If twelve polls pass with nothing, end your turn with 'P1b: nothing received after 120s.' Write no files beyond nothing; run no git commands.

- **H′ predicts:** the live dispatcher **does** receive the completion in its own loop — this is the corpus finding replicated live on the pinned CLI.
- **Falsifier:** the live dispatcher receives nothing and the result lands at the root anyway → H′'s liveness clause is wrong, and the topology is a star unconditionally.
- **Why it matters:** P1-a vs P1-b is the whole experiment. Same dispatch parameters, one variable changed.

### P2-a — synchronous collection, single dispatch *(the control arm)*

Dispatch `subagent_type: researcher`, `description: "probe-manager-2a"`, prompt:

> Dispatch a child agent with `run_in_background: false` — pass that parameter explicitly — and the prompt 'Reply with exactly: MARKER-P2A-CHILD'. Include the child's exact reply, quoted, in your final message. State explicitly the value you passed for `run_in_background`. Write no files. Run no git commands.

- **Verdict test:** `MARKER-P2A-CHILD` appears verbatim in the manager's return, **and** the manager's transcript shows `"run_in_background": false` in the actual tool-use input.
- **H′ predicts:** reliable.

### P2-b — fan-out: parallel dispatches collected in one turn *(ledger row 7; the idiom phase 2 would sanction)*

Dispatch `subagent_type: researcher`, `description: "probe-manager-2b"`, prompt:

> In a **single message**, dispatch three child agents concurrently, each with `run_in_background: false` passed explicitly, with the prompts 'Reply with exactly: MARKER-P2B-ONE', 'Reply with exactly: MARKER-P2B-TWO', and 'Reply with exactly: MARKER-P2B-THREE'. Collect all three in that same turn and quote all three replies verbatim in your final message. Report whether all three results returned to you, and state the `run_in_background` value you passed for each. Write no files. Run no git commands.

- **Verdict test:** all three markers appear verbatim in the manager's return; the transcript confirms three tool-use blocks in one assistant message, each with `"run_in_background": false`.
- **H′ predicts:** reliable — the synchronous window admits parallel dispatch. **This is the arm that licenses phase 2's fan-out clause.**
- **Falsifier:** fewer than three collected, or any of them surfacing at the root → the sanctioned idiom does not survive fan-out, which changes phase 2's landing materially.

### P2-c — type control

Repeat **P2-a** exactly, with `subagent_type: manager` and `description: "probe-manager-2c"`, marker `MARKER-P2C-CHILD`.

- **Predicts:** identical behavior. Confirms the P1–P4 verdicts are not artifacts of the read-only agent type the behavioral probes use.
- **Falsifier:** behavior differs by agent type → every other verdict is type-scoped and must say so.

### P3 — upward addressing *(three arms)*

Dispatch `subagent_type: researcher`, `description: "probe-manager-3"`, prompt:

> First, note your own agent id if you can determine it. Then dispatch a child with `run_in_background: false` passed explicitly, whose prompt is: 'Attempt to send a message to your dispatcher using SendMessage, three times, and report the verbatim outcome or error text of each attempt as your final reply: (1) to the name `researcher`; (2) to the raw agent id `<PARENT_ID>`; (3) to `main`. Report each attempt separately and verbatim — do not summarize.' Substitute your own agent id for `<PARENT_ID>` if you know it; if you cannot determine your own id, say so explicitly and have the child attempt only (1) and (3). Relay the child's verbatim report in your final message. Write no files. Run no git commands.

Then repeat the whole probe with the **child dispatched `run_in_background: true`** (`description: "probe-manager-3b"`), since a background child may have a different channel than a foreground one — the SendMessage surface documents `main` as available to background subagents specifically.

- **H′ predicts:** no route to the *parent* exists by any addressing scheme; error text captured for each.
- **Falsifier:** the child reaches its parent → the asymmetry claim dies and instances 2/7/8 need another explanation.
- **Third outcome, neither confirm nor falsify:** the child reaches `main`. That is an upward channel to the **root**, not to the parent — it confirms the star and simultaneously reveals a sanctioned recovery path. Flag it prominently; phase 2 must know.

### P4-a — the continuation path *(instance 8's mechanism, as chartered)*

Dispatch `subagent_type: researcher`, `description: "probe-manager-4a"`, prompt:

> Dispatch a child with `run_in_background: false` passed explicitly and the prompt 'Reply with exactly: MARKER-P4-FIRST'. Quote its reply and its `agentId` line verbatim, then end your turn with: 'P4: collected; awaiting instruction.' Write no files. Run no git commands.

Then, from the root, SendMessage the manager by id:

> Ask your completed child a follow-up via SendMessage, addressing it by the agent id you captured: it should reply with exactly 'MARKER-P4-SECOND'. Report verbatim what returns to you — including the verbatim result of the SendMessage call itself — then end your turn.

Record where `MARKER-P4-SECOND` actually surfaces: in the manager's next return, or stranded at the root. Capture the SendMessage tool result verbatim — its own text is behavior-grade evidence about whether the resumed agent runs in background.

- **H′ predicts:** the manager sends, then ends its turn; the continuation's answer has no live collection point below the root and falls through to the root.

### P4-b — continuation with a live dispatcher

Same as P4-a, but the root's second message instructs:

> …then **stay alive**: poll with short Bash `sleep` commands (10s, up to 12) until the child's answer arrives. Quote it verbatim when it does, then end your turn. If nothing arrives in 120s, say so.

- **H′ predicts:** the live dispatcher receives the continuation's answer — making the continuation rule a *liveness* rule rather than a prohibition, which is precisely the distinction phase 2's landing (b) turns on.
- **Falsifier:** the answer lands at the root even with the dispatcher live → continuations are structurally different from dispatches, and the prohibition form is correct.
