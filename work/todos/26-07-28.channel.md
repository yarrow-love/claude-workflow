# Phase 1 — channel: hold-open mechanics and the read-only boundary

## Feature Request

> executor@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

Seeded from [`work/milestones/1.spike/1.channel.md`](../milestones/1.spike/1.channel.md), which stays the spec and the record — **read it in full before planning**; this order carries the acceptance criteria and the campaign's confirmed decisions, not the full rationale. Campaign log: [`26-07-28.execute-m1-spike.md`](26-07-28.execute-m1-spike.md).

**The objective.** Establish empirically whether a held-open `claude -p --input-format stream-json --output-format stream-json` process against a real large session is (a) a *session* — capturable id, live-appending transcript, resumable after its process dies — (b) an *observable* one, emitting a usable per-turn event wire, and (c) a *bounded* one, able to answer consults without acquiring the ability to act.

**This phase can end the mission, and that is a success.** It carries both of mission v4's refutation-shaped failure criteria. If live transcript append, the event wire, or the read-only boundary cannot be demonstrated, **stop and escalate with the refuting evidence** — do not engineer around it. A refutation here is a completed phase, not a failed one.

**The consult handle.** The last `architect@…` entry above is the milestone architect. Note that it is the same session as the campaign Executor — an artefact of this milestone being planned and executed in one flagship session. Consult it for plan-interpretation questions via `.claude/bin/consult`; genuinely new design decisions still escalate.

### Confirmed decisions — settled at the Reconnaissance gate, not open for re-litigation

These were fixed after two researcher passes found four defects in the phase doc as first written. The doc has been amended to carry them; they are restated here because they are the ones most likely to be silently re-invented.

1. **The vehicle is passed as an explicit argument** — `76ba13c6-e6f5-4933-9e6c-7ef3fbdd6b7d` (6,456,439 bytes, `cwd` verified as this repo). The harness must **not** auto-select "the largest transcript": no documented mechanism exposes a session's own id to a script it invokes, so the exclusion could not be implemented safely and a buggy one could fork the hosting session's live transcript. If the vehicle is absent at run time, escalate — never substitute a trivial session.
2. **`--fork-session` is mandatory.** Without it, resume mutates a real recorded session in place. The spike never writes into a transcript it did not create.
3. **Pin `--model fable` explicitly on every spawn.** It is *not* one of `consult`'s five read-only layers — it is a separate flag, defaulted there — so "reproduce the five layers" leaves it unset. The prompt cache keys on the byte-exact prefix and system-prompt content varies with model; an unpinned model would invalidate phase 2's entire matrix.
4. **Harness topology: a channel primitive + a driver**, not a monolith — phase 2 extends this with a matrix driver and a fork-measurement path.
5. **Bun `spawn` mechanics** (bun 1.3.14; all four existing `.claude/bin/` scripts are `spawnSync`, so there is no in-repo precedent): `stdin` is a `FileSink`, so **`.write()` must be followed by `.flush()`** per turn or turn N+1 silently never arrives; **EOF comes from `proc.stdin.end()`, never `proc.kill()`**; and **stdout *and* stderr must be drained concurrently** with the exit promise or the OS pipe buffer deadlocks.
6. **Discovery is two-stage.** Observe the turn-completion signal on turn 1 before driving turns 2–3 automatically; "discover and use" is not one step.
7. **Trivial canned turns** for the ≥3-turn demonstration; boundary probes ride the *same* channel as turns N+1/N+2, demarcated in the run log so refusal turns are never folded into the wire-format evidence.
8. **Artifacts**: harness → `work/milestones/1.spike/harness/` (tracked, archives with the mission); raw stream logs → `tmp/spike/` (gitignored, declared in `work/PROJECT.md` § Structure). **Nothing lands under `.claude/`** — no `consult` edits, no new bin script, no BASELINE amendment. Record, do not repair, any DENY-list drift found.

### What phase 2 needs from this phase

Its matrix design depends on criterion 5's answer about where `usage` rides. If per-turn `usage` is **not** emitted inside a multi-turn streaming process, say so plainly and prominently — phase 2 must then restructure to one process per measured turn, which weakens the very comparison the spike exists to make. Criterion 12's last-touch timestamp is the clock phase 2's cold baseline depends on.

## Acceptance

> executor@play/c1378142-cf5c-4ad2-97b0-920533f97a7c

Carried verbatim from the milestone phase doc. Headlessly verifiable unless marked.

1. **The harness exists and runs.** `work/milestones/1.spike/harness/` holds a bun script that runs from the repo root; invoked with no arguments it prints usage to stderr and exits 1. A completed run leaves a raw stream log under `tmp/spike/`.
2. **Multi-turn hold-open is demonstrated.** One channel process accepted **≥3 successive user turns on one stdin without respawn**, each producing an assistant answer. The stdin message shape and the turn-completion signal are written down in the addendum, verbatim enough to reimplement from.
3. **The session id is captured** from the `system` / `init` event and recorded in the run log.
4. **Live transcript append is demonstrated *while the process is alive*.** Record the byte size and line count of `~/.claude/projects/<repo-slug>/<captured-id>.jsonl` after turn 1 and again after turn 2, both sampled **before** the process exits, and show growth between them. Sampling only at exit does not satisfy this criterion — the distinction is the whole point of D4's transcript half.
5. **The event wire is characterised.** The event types emitted across a full run are enumerated, and the location of `usage` (which event, which fields of `input_tokens` / `output_tokens` / `cache_read_input_tokens` / `cache_creation_input_tokens` are present) is stated as fact, including the negative case if per-turn usage is not emitted.
6. **Clean death and post-mortem resume.** After EOF the process exits; its exit code is recorded; then `claude -p --resume <captured-id> --fork-session …` from the repo root returns an answer that demonstrably references the channel conversation. The channel's transcript survives its process.
7. **The read-only boundary holds.** With the five-layer construction applied, the channel refused both a write attempt and a shell-command attempt; the refusals are recorded verbatim. Any DENY-list drift against v2.1.220 is recorded (not repaired).
8. **Surface visibility is recorded as a finding, not a gate** (operator ruling 1). The CLI half is headless-checkable: state whether the live channel session appears in `claude --resume`'s listing. **The Desktop-surface half is operator-gated** — the Executor stages it as a recipe for the operator to run and report, and does not stall on it.
9. **Findings appended to the evidence note** — a dated section in `work/notes/26-07-28.consult-token-cost-evidence.md` covering criteria 2–8, section-stamped per `work/README.md` § The callback grammar.
10. **The gate is called — operator-gated.** If criterion 4 (live append), criterion 5 (the event wire), or criterion 7 (the boundary) fails, the phase does **not** work around it: it stops, records the refuting evidence, and escalates. These are charter failure criteria 1 and 2, and a refutation here is a successful phase, not a failed one.
11. **No product changed.** `git status` shows no modification under `.claude/`.
12. **The vehicle's last-touch timestamp is recorded** — the wall-clock instant of the final API call this phase made against the vehicle prefix, *including the boundary-probe refusals*, stated explicitly in the addendum. Phase 2's opening idle gap is measured from this instant; without it, phase 2 must reconstruct the clock from raw logs and may under-cool its cold baseline.
13. **No hook artifacts appeared.** The repo wires `SessionEnd → session-archive` and `Stop → commit-guard`; the spawn's `disableAllHooks: true` should suppress both. Verify by inspection after the run: no new file under `work/sessions/`, no new `tmp/commit-guard/` marker attributable to the channel's session id, and a clean `git status`. A hook that fired despite the setting is a finding worth recording — and `commit-guard` returning a block decision is a live candidate explanation if the child ever fails to exit cleanly on EOF (criterion 6).
14. **The DENY-drift audit states its method.** Whatever method is used to compare `consult`'s DENY array against v2.1.220's deferred/built-in registry, say which it was. A cosmetic "matches no known tool" stderr warning is *expected* and is not by itself evidence of drift — do not manufacture a finding from it.
